# Build Evidence-First Reconciliation, Then Measure Safely

**Invoice Reconciliation should build a rules-first selective reconciliation system, not a general-purpose invoice agent.** The system should deterministically join the latest authorized purchase-order state to buyer-controlled receipt or acceptance evidence, recompute quantities and money with fixed-decimal or integer arithmetic, and invoke a small open model on Fireworks only for bounded semantic ambiguity. It should evaluate whether this cascade reduces human review at a fixed safety constraint, using the same frozen held-out cases and scoring as a version-pinned, actually accessible frontier-model baseline. The benchmark should be a repository-owned synthetic set because the reviewed public document datasets test extraction rather than linked PO, invoice, and receiving reconciliation; FATURA is useful as an explicitly CC BY 4.0 image-layout diagnostic, while DocILE's data license remains unverified. No application, model run, calibration, latency test, or cost measurement exists yet, so every result must remain **Not run** and the work must not claim superiority or production readiness. The narrow demonstration should cover exact matches, stale invoices after short receipt, and one semantic or UOM ambiguity that safely abstains. Submission work is urgent: organizers recommend starting submission by 3:30 PM Pacific and require processing by 4:30 PM on November 2, 2026, while the present private repository conflicts with the published requirement for a public, permission-free repository during judging ([official resources](https://hackersquad.io/events/fireworks-deploy-with-microsoft-nvidia/resources); [official rules](https://hackersquad.io/events/fireworks-deploy-with-microsoft-nvidia/resources?tab=rules)).

## Buyer-controlled evidence makes the core decision trustworthy

The root problem is not merely extracting invoice fields. It is deciding whether a billed quantity and price are supported by the latest authorization and by what the buyer actually received or accepted. Microsoft Dynamics 365 describes three-way matching as a price comparison plus invoice quantity against selected product receipts, while Oracle distinguishes two-way matching, three-way matching with received quantity, and four-way matching with accepted quantity ([Microsoft Dynamics 365](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/accounts-payable-invoice-matching); [Oracle Payables](https://docs.oracle.com/cd/A60725_05/html/comnls/us/ap/point04.htm)). **A PO authorizes terms, but does not prove delivery. An ASN or packing slip records what the supplier says it shipped, but does not prove what the buyer received.** Oracle documents the ASN as a supplier message used later to create a receipt after goods arrive, and records a packing-slip number as receipt-header metadata rather than an independent receipt event ([Oracle ASN process](https://docs.oracle.com/cd/A60725_05/html/comnls/us/po/cpoasn.htm); [Oracle receipt headers](https://docs.oracle.com/cd/A60725_05/html/comnls/us/po/rcts06.htm)).

The MVP should therefore compare an invoice against the effective PO or contract version and a net buyer-controlled receipt or acceptance ledger. Each receipt event should carry an immutable ID, timestamp, source system or actor, PO and line reference, quantity, unit of measure, and any reversal. The configured `match_basis` must say whether the policy requires shipment, receipt, or acceptance. A supplier packing slip, ASN, or carrier record can support provenance, but it must not override buyer evidence. If receipt or acceptance evidence is missing, the factual result is `INSUFFICIENT_EVIDENCE`, not a claim that goods were not delivered.

The core architecture should be a deterministic cascade:

| Stage | Responsibility | Safety behavior |
|---|---|---|
| Evidence ingest | Hash and version documents and events; preserve source IDs and original values | Treat all document text as untrusted data |
| Canonicalization | Normalize IDs and dates; represent quantities as integers or rationals; represent money as integer minor units or fixed decimals | Reject unknown currency, UOM, or destructive normalization |
| Ledger construction | Aggregate net receipt or acceptance, reversals, prior invoices, and credits by PO line | Fail closed on missing or contradictory state |
| Exact reconciliation | Join PO version, line, buyer SKU, approved aliases, currency, and UOM; recompute totals | Apply only configured, effective-dated tolerances |
| Ambiguity packet | Send one unresolved invoice line and a small supplied candidate set to the model | Exclude unrelated pages and embedded instructions |
| Model assistance | Rank supplied candidates or choose among supplied extraction alternatives | No arithmetic, policy invention, free-form tools, or financial action |
| Validation and policy | Validate schema, candidate IDs, evidence IDs, and deterministic recomputation; then apply review policy | Malformed, unsupported, or ambiguous output goes to review |

This division follows established invoice-matching controls and research on selective prediction and cascades. Commercial matching systems apply explicit quantity, price, charge, and total rules; selective classification adds a reject option so risk can be traded against coverage; FrugalGPT demonstrates the general efficiency pattern of routing work through different model and prompt paths, but does not establish invoice results ([Microsoft Dynamics 365](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/accounts-payable-invoice-matching); [Oracle tolerances](https://docs.oracle.com/en/cloud/saas/financials/25d/fappp/invoice-tolerances.html); [Geifman and El-Yaniv](https://arxiv.org/html/1705.08500); [FrugalGPT](https://arxiv.org/html/2305.05176)). **The open model's role is semantic matching under constraint, not authoritative calculation or approval.**

The deterministic layer should own PO version selection, exact line and SKU joins, approved alias lookup, cumulative quantity arithmetic, rational UOM conversion, duplicate fingerprints, price and total recomputation, tolerance lookup, effective dates, and policy state. It should compute `remaining_billable = net_received_or_accepted - prior_net_billed` before evaluating the current invoice. Dynamics documents that previously posted invoice lines affect price-total matching, which confirms that partial receipts and multiple invoices require cumulative state rather than isolated document comparison ([Microsoft Dynamics 365](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/accounts-payable-invoice-matching)).

The model should receive only unresolved evidence and supplied candidate IDs. Safe tasks include ranking semantically similar descriptions, choosing among OCR alternatives already tied to source spans, or proposing a likely category such as item, tax, or freight for deterministic verification. It must not invent aliases, conversion factors, tolerances, FX rates, receipt facts, or payable amounts. Any score used for routing must be calibrated against observed task-specific correctness; natural-language self-confidence is not a safety gate because neural confidence is often miscalibrated and published calibration results do not validate a generative model's self-report on invoices ([Guo et al.](https://proceedings.mlr.press/v70/guo17a.html); [Xin et al.](https://aclanthology.org/2021.acl-long.84/)).

The output must separate **reconciliation facts** from **review policy**. A clear short receipt can be a certain `DISCREPANCY`, while policy separately decides whether a human must confirm, request a credit, or hold the invoice. Conversely, an arithmetically exact invoice can still require review because receipt evidence is stale or incomplete. `AUTO_RESOLVE` is only a benchmark classification or proposed disposition. It must never transfer money, post an invoice, release a hold, alter a PO, create a receipt, contact a supplier, or change supplier banking information.

Evidence-linked output should include the case and policy version, reconciliation status, proposed action, review requirement and reason codes, invoice and PO line IDs, receipt event IDs, normalized and original values, discrepancy kinds, deterministic check results, and source-span references. The application must reject unknown fields, nonexistent evidence IDs, candidate IDs not supplied in the request, arithmetic asserted by the model, unsupported aliases, and invalid enum values. OWASP warns that instructions embedded in external files can manipulate connected decisions and recommends strict output formats, least privilege, segregation of external content, deterministic validation, and human approval for high-risk actions ([OWASP LLM01](https://genai.owasp.org/llmrisk/llm01-prompt-injection/)). For this demo, all access should be read-only and document phrases such as "ignore prior rules" must remain inert data.

### Recommended same-day scope

The build should include one currency, goods rather than services, immutable PO versions, buyer-controlled receipt evidence, exact or approved alias matching, approved rational UOM conversion, partial receipts and prior invoices in a simplified ledger, duplicate suspicion, fixed-decimal totals, and explicit tolerances. The central discrepancy should be the user's original scenario: the supplier-side documents may still show ten units, but the buyer receipt records eight and the invoice bills ten. The system should report an overbilled quantity of two and cite the invoice and receipt lines. It should not state an unsupported corrected amount unless the frozen policy and complete line-level evidence deterministically establish a **proposed** payable amount.

Tax, freight, discounts, foreign exchange, returns, receipt reversals, credits, services, milestone billing, retainage, and jurisdiction-specific accounting should be excluded from the core demo unless exact source values and policy are supplied. Dynamics and Oracle treat charges, tax, round-off, accounting currency, and exchange-rate variance as separate controls, so collapsing them into a generic price mismatch would be misleading ([Microsoft Dynamics 365](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/accounts-payable-invoice-matching); [Oracle tolerances](https://docs.oracle.com/en/cloud/saas/financials/25d/fappp/invoice-tolerances.html)). These exclusions protect the central claim: accurate, efficient routing on a narrow and auditable task.

## Synthetic paired cases measure reconciliation, while public sets diagnose extraction

The reviewed public datasets are useful, but most answer a different question. DocILE evaluates key information localization and line-item recognition in semi-structured business documents; CORD and SROIE focus on receipt OCR and parsing; FUNSD focuses on forms; FinTabNet focuses on table structure ([DocILE paper](https://arxiv.org/html/2302.05658); [CORD](https://github.com/clovaai/cord); [SROIE](https://arxiv.org/html/2103.10213); [FUNSD](https://guillaumejaume.github.io/FUNSD/); [FinTabNet paper](https://arxiv.org/html/2005.00589)). **Extraction success is not reconciliation safety.** A system can extract every field correctly and still authorize an unsupported quantity because it linked the wrong PO version, ignored prior billing, or treated a packing slip as receipt evidence.

The bounded search did not verify a dedicated public benchmark containing linked purchase orders, supplier invoices, buyer receipts or acceptances, line-level discrepancies, and ground-truth safe-auto-resolution versus human-review labels. This is not a claim that no such dataset exists. It means the project should state: **"We did not verify a dedicated public line-level three-way matching benchmark in our bounded search as of November 2, 2026."**

The best recommendation is a repository-owned, deterministic synthetic benchmark with two layers. A structured JSON layer should isolate matching, arithmetic, and policy reasoning from OCR. A smaller rendered PDF or image layer should add controlled layout and OCR noise for end-to-end diagnosis. Every case should originate from a canonical transaction object and an explicit mutation such as short receipt, stale removed line, price variance, duplicate invoice, missing receipt, approved alias, missing UOM conversion, conflicting evidence, or exact match. Each record should preserve the generator version, seed, vendor family, template family, scenario family, mutation list, expected calculations, policy version, split, and human verification status.

FATURA is the cleanest public image-layout diagnostic for the buildathon. Its Zenodo record identifies 10,000 synthetic invoice images generated from 50 templates and licenses the data under CC BY 4.0; it also distinguishes known-template from unseen-template evaluation ([FATURA Zenodo record](https://zenodo.org/api/records/8261508); [FATURA paper](https://arxiv.org/html/2311.11856)). Use a small attributed subset if needed, or use its layout-diversity idea when generating repository-owned documents. FATURA contains invoices only, so it cannot supply reconciliation ground truth.

DocILE is highly relevant for invoice field and line-item extraction, with about 6,700 annotated documents, 100,000 synthetic documents, nearly one million unlabeled documents, and 55 annotated classes, but its download is token-gated and the reviewed official pages did not expose a separate data license. The repository's MIT license explicitly covers software, not necessarily the dataset ([DocILE paper](https://arxiv.org/html/2302.05658); [DocILE repository](https://github.com/rossumai/docile); [software license](https://raw.githubusercontent.com/rossumai/docile/main/LICENSE)). **Do not recommend unqualified redistribution or commercial reuse of DocILE data until its data terms are verified.** This is a key example of why a code license cannot be laundered into a data license.

FinBalance is the closest verified adjacent benchmark and a useful methodological reference. It provides synthetic multi-document accounting records, deterministic expected journal entries, balance sheets, and inconsistency codes; its generated data is CC BY 4.0 and its code is Apache-2.0 ([FinBalance paper](https://arxiv.org/html/2606.15949); [repository](https://github.com/Devansh1105/finbalance); [data license](https://raw.githubusercontent.com/Devansh1105/finbalance/main/DATA_LICENSE.md)). Its public splits contain 143 coverage records and 710 main-evaluation records, but it is not a dedicated three-way line-item benchmark. The reviewed repository includes invoice and goods-receipt scenarios but no verified purchase-order document type. Its scores are therefore not directly comparable. Its trusted contribution is design practice: deterministic generation, seeded manifests, explicit inconsistencies, frozen artifacts, saved outputs, and paired analysis.

The benchmark should split cases by vendor or supplier family, layout or template family, and discrepancy scenario family. FATURA and DocILE both provide precedent for template or layout-disjoint evaluation rather than cosmetic random page splits ([FATURA Zenodo record](https://zenodo.org/api/records/8261508); [DocILE paper](https://arxiv.org/html/2302.05658)). Thresholds, prompts, aliases, examples, and rules must be tuned only on development cases. Held-out labels and policy should be frozen and hashed before test runs. Every held-out case should be hand-checked against its source JSON and policy, with two reviewers on ambiguous or safety-critical cases where time permits.

For a same-day demonstration, a reasonable target is 80 to 150 structured development cases, 200 to 300 held-out structured cases, and a 60 to 120 case noisy rendered slice. The event rules describe 100 or more varied held-out examples as an evidence target where feasible, not a universal entry minimum ([official rules](https://hackersquad.io/events/fireworks-deploy-with-microsoft-nvidia/resources?tab=rules)). If the team cannot construct a defensible larger set, it should prefer a smaller audited benchmark over inflated near-duplicates. Synthetic results demonstrate controlled performance only. They do not establish performance on real enterprise data, production safety, legal compliance, fraud detection, or authorization to pay.

## Safety-constrained evaluation makes fewer reviews meaningful

The comparison must hold the cases, policy, schema, and evaluator constant. The required arms are:

| Arm | Purpose |
|---|---|
| Rules-only | Establish what exact joins, arithmetic, evidence checks, and tolerances solve without an LLM |
| Frontier baseline | Use one version-pinned and actually accessible frontier model with the same evidence, policy, and output schema |
| Open model, simple harness | Measure the selected open model without the engineered reconciliation pipeline |
| Engineered hybrid | Measure deterministic reconciliation plus bounded open-model ambiguity handling |

The frontier baseline must be named only after the team confirms access and records the exact provider model identifier or snapshot, configuration, prompt, and timestamp. Speech references to "Gev," "Jeb," or "Jeff" were ambiguous and must not be treated as a model name. Save baseline raw outputs before provider behavior changes. If the frontier and hybrid receive different evidence quality, report separate tracks: a reasoning track where every arm receives identical normalized records, and a system track where each arm receives identical rendered documents and pays for its own extraction.

The primary objective should be:

> Among systems whose held-out unsafe-auto-resolution upper confidence bound and human-required recall satisfy predeclared proposed safety criteria, select the system with the lowest review rate. Use total token cost and p95 end-to-end latency as tie-breakers.

Any numeric safety threshold is a **proposal requiring stakeholder agreement**, not an accepted financial control. If no arm satisfies the criterion, report that result and declare no winner. Do not choose whichever metric looks favorable after the run.

The denominators must remain explicit:

| Metric | Definition |
|---|---|
| Unsafe auto-resolution rate | Unsafe automatic recommendations / all automatic recommendations |
| Unsafe auto-resolutions among all cases | Unsafe automatic recommendations / all evaluable cases |
| Missed-human-required rate | Human-required cases automatically recommended / all ground-truth human-required cases |
| Human-required recall | Human-required cases sent to review / all ground-truth human-required cases |
| Review rate | Cases sent to review / all evaluable cases |
| Auto-resolution coverage | Automatic recommendations / all evaluable cases |
| Auto-resolution precision | Correct automatic recommendations / all automatic recommendations |
| Supported amount exact accuracy | Exact deterministically supported amount outputs / cases where the amount is defined |

**Unsafe auto-resolution rate and missed-human-required rate are different quantities.** The first conditions on what the system automated; the second conditions on cases that truly required a human. Both should be shown as counts and rates. Review rate is meaningful only when compared at the same safety constraint. Also report per-class precision, recall, macro-F1, a confusion matrix, discrepancy-type metrics, evidence-reference validity, exact and absolute amount error where defined, and scenario-stratified results.

Selective prediction research motivates risk-versus-coverage analysis, but it does not supply a valid invoice threshold ([Geifman and El-Yaniv](https://arxiv.org/html/1705.08500); [Xin et al.](https://aclanthology.org/2021.acl-long.84/)). Vary only a development-chosen routing threshold when drawing a risk-coverage curve. The routing signal should be an observed and calibrated task-specific score, such as margin between supplied candidates or validation outcomes, not a model's prose confidence. Keep deterministic gates for missing evidence, invalid schema, unsupported UOM, conflicting records, and uncertain critical fields.

Report exact binomial confidence intervals for safety proportions and paired uncertainty for arm differences. NIST recommends exact binomial methods for small samples or few failures ([NIST exact binomial guidance](https://www.itl.nist.gov/div898/software/dataplot/refman2/auxillar/exacbino.htm)). Zero observed unsafe recommendations is not proof of zero risk. With zero failures among 100 automatic cases, the approximate one-sided 95% upper bound is about 3%; among 300 automatic cases it is about 1%. The denominator is the number of automatic cases, not the total benchmark. Shared templates and scenarios also weaken independence, so family-level or clustered resampling is preferable when practical.

Every run should record prompt and schema hashes, requested and returned model identifiers, provider, timestamp, decoding settings, seed if supported, context and output limits, tools, timeout and retry policy, OCR engine and settings, retrieval version, parser and repair behavior, cache state, raw output where terms permit, per-attempt token usage, errors, latency, and cost. Thresholds and prompts must be locked on development data before held-out evaluation. Count all retries, failed attempts, OCR calls, embeddings, repair calls, cached tokens, and tool costs. End-to-end latency should include retries and report p50 and p95, with cold, warm, and cache-hit conditions identified.

## Fireworks fits the ambiguity layer, not the accounting core

Fireworks provides an OpenAI-compatible endpoint at `https://api.fireworks.ai/inference/v1`, structured JSON outputs, prompt caching, usage fields, serverless inference, optional batch evaluation, and optional training ([Serverless quickstart](https://docs.fireworks.ai/getting-started/quickstart); [Structured Outputs](https://docs.fireworks.ai/structured-responses/structured-response-formatting); [Prompt caching](https://docs.fireworks.ai/guides/prompt-caching); [Batch API](https://docs.fireworks.ai/guides/batch-inference)). The best buildathon use is a synchronous Serverless call for residual ambiguity after exact checks. Fine-tuning, dedicated deployment, vision deployment, and Batch are optional extensions, not prerequisites.

The current official quickstart and structured-output guide use `accounts/fireworks/models/glm-5p3-flash`. The live pricing page accessed November 2, 2026 lists Standard rates of **$0.15 per million input tokens, $0.03 per million cached input tokens, and $0.50 per million output tokens**, with higher Priority rates ([quickstart](https://docs.fireworks.ai/getting-started/quickstart); [pricing](https://docs.fireworks.ai/serverless/pricing)). These are dated official prices, not measured application cost. A catalog or documentation listing does not prove access, quota, region, spend tier, or feature availability in the team's account. Confirm account access before naming this model as the evaluated arm, and re-read live pricing before publishing cost results.

The request should use a narrow JSON Schema and repeat the schema in the prompt because Fireworks states that the model does not automatically see the schema. The client must explicitly request JSON, detect `finish_reason="length"`, reject truncated or malformed output, and validate locally. Fireworks also notes that `json_schema` disables separate reasoning output, so the team should prioritize a compact auditable result over free-form chain-of-thought ([Structured Outputs](https://docs.fireworks.ai/structured-responses/structured-response-formatting)). The system should not depend on hidden reasoning or expose it as evidence.

Prompt caching is enabled by default. Place a byte-stable policy, instructions, examples, and schema prefix first, then append the small variable ambiguity packet. Log input, cached-input, and output tokens from the API's `usage` object, which Fireworks identifies as the billing source of truth ([Prompt caching](https://docs.fireworks.ai/guides/prompt-caching); [Serverless overview](https://docs.fireworks.ai/serverless/overview)). Cache savings must be measured, not inferred. Use cache isolation where appropriate, and never allow one customer's document content to become another customer's prompt prefix.

Retry 429 and transient 500, 502, 503, and 504 failures with bounded exponential backoff and jitter; do not blindly retry 400, 401, 404, or 422 errors. Client logs must include connection failures that may not appear in provider analytics ([Fireworks reliability guide](https://docs.fireworks.ai/guides/reliability)). A schema failure, timeout, exhausted retry budget, or missing usage record should become a visible failed attempt and a review route, not a silent pass.

The asynchronous Batch API is designed for evaluation and is billed at 50% of standard Serverless token rates, but model compatibility varies and unsupported models can remain pending ([Batch API](https://docs.fireworks.ai/guides/batch-inference)). Use synchronous calls for the demo and only switch a stable benchmark harness to Batch after confirming compatibility. Near the submission deadline, asynchronous queue risk is more important than theoretical savings.

Fine-tuning is optional under both Fireworks documentation and event rules. Fireworks describes supervised fine-tuning as suitable for extraction and classification and generally requiring hundreds of good examples, which is unlikely to be the best use of a single afternoon before a frozen benchmark exists ([Fireworks training overview](https://docs.fireworks.ai/fine-tuning/finetuning-intro); [official rules](https://hackersquad.io/events/fireworks-deploy-with-microsoft-nvidia/resources?tab=rules)). The project should treat fine-tuning as a future ablation, not an MVP dependency.

Microsoft Document Intelligence's prebuilt invoice model is a credible optional extraction layer for PDFs or images, and NVIDIA NIM is a credible optional self-hosted serving route ([Microsoft invoice model](https://learn.microsoft.com/azure/ai-services/document-intelligence/prebuilt/invoice?view=doc-intel-4.0.0); [NVIDIA NIM for VLMs](https://docs.nvidia.com/nim/vision-language-models/latest/introduction.html)). **No public event rule reviewed requires Azure deployment, NVIDIA hardware, or fine-tuning.** Add these only if an authenticated sponsor-track requirement or a measured extraction bottleneck justifies the work.

Security and release hygiene are non-negotiable. Store keys only in environment variables, commit only placeholder names, and keep real invoices, customer data, supplier identities, addresses, tax IDs, bank details, signatures, billing identifiers, and embedded metadata out of the repository. Save synthetic or explicitly licensed artifacts only. If provider terms restrict raw frontier outputs, retain allowed hashes, aggregate metrics, metadata, and a rerun procedure while disclosing the limitation.

## Conclusion

The strongest hackathon entry is not the system that automates the most invoices. It is the system that proves, on frozen paired evidence, that it can reduce review only after deterministic controls and calibrated abstention protect human-required cases. This framing turns open-model reasoning into a narrow semantic component inside an auditable financial-control pipeline rather than an unbounded financial agent.

The main unresolved risks are evidentiary rather than architectural: no benchmark has run, no threshold has stakeholder approval, account access to the documented Fireworks model is unverified, real-world generalization is unknown, and the private repository conflicts with the official public-access rule. A credible submission can still be completed by freezing the benchmark, running the four fair arms, saving every artifact, keeping all scores as **Not run** until measured, and making an explicit owner decision about repository eligibility before the processing deadline.
