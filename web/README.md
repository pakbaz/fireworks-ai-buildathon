# Review site

The webapp for the demo, with two views and no build step:

- **Compare:** Kimi K3 alone, Kimi K3 + our harness, and GLM 5.3 Flash + our harness on the same invoices, with a button that runs one invoice through all three on Fireworks.
- **Review queue:** the analyst dashboard from [dashboard/](../dashboard/README.md): a threshold dial, a queue ranked by expected loss, and scans with the disputed values highlighted.

```bash
python3 web/server.py
```

Open http://127.0.0.1:8765/web/. Live runs need `FIREWORKS_API_KEY` in the git-ignored `.env`, and the key stays on the server. Use this server, and not `python3 -m http.server` from the repo root, which would serve `.env`.

| File | Role |
|---|---|
| `server.py` | Serves only `web/` and `data/images/` on localhost, and runs the arms through `harness.api.analyze` |
| `index.html`, `styles.css` | The page |
| `compare.js`, `compare.json` | The Compare view and its data. Generated by `python3 web/build_compare.py`, with no model calls |
| `app.js` | The Review queue view |
| `cases.json` | The 25 flagged cases with scans. Generated, do not edit |
| `build_data.py` | Rebuilds `cases.json` from saved files, with no model calls: `python3 web/build_data.py` |

## How the claims are tested

`build_compare.py` scores each arm on the invoices every arm finished, and tests two claims per test set with rules fixed in the code. The page shows the outcome, including when a claim falls short.

- **GLM 5.3 Flash + harness performs at Kimi K3's level:** catch rate within 1 point of Kimi K3 alone, and false alarm rate no more than 1 point above it.
- **Kimi K3 + harness outperforms Kimi K3:** catches at least as many, raises no more false alarms, and is strictly better on one of the two.

The GLM arm is `runs/glm_harness_wiki_low` (low reasoning), and live calls use the same setting. Kimi K3 + harness ran on the first 300 document invoices, so the 1,000-invoice view compares two arms.

Limits: the data is synthetic, and the history set covers the seven anomaly types the checks were written for. Kimi K3 alone on the document sets ran before its prompt gained the history instruction. All arms read document text, not the scans. On scans, GLM is well behind Kimi K3 (see [results.md](../results.md)).

## What is real and what is not (Review queue)

- Cases and scans come from `data/test.jsonl` and `data/images/`. All synthetic.
- Risk, dollars at risk and ranking come from `runs/kimi_alone/test.jsonl`, run on text. They are not harness results.
- Headlines and highlighted values come from the answer key (`label`). A live app needs them from the harness.
- Where Kimi K3 and the answer key disagree (TEST-00403), the page says so on the case.
- The ÷5 caution margin behind Northside's suggested $2 is a proposal, and `wiki/policy.json` has no such field.

## Changes from the design

- **Upload:** "Try a sample" adds a held-back case from the saved run and says so. Real files get listed and a note that they were not read. The design ran a fake "reading" step and returned the same case for any file.
- **Add supplier notes or policy:** removed, because nothing stored the files or approved them.
- **Undo:** works per company. In the design it could restore a case from the other company.
- **Partly billed POs:** the PO crop notes what is left to bill, so "Ordered 426" next to "Billed 26" makes sense (TEST-00256).
- **Why it ranks:** also shows the `harness/dial.py` comparison and Kimi K3's explanation.

## Escalation rule

The page escalates when expected loss is above the dial's dollar threshold. `harness/dial.py` compares expected loss with `(1 - risk) × review cost`. On these 25 cases `dial.py` escalates all of them, so a dial built on it would have nothing to move. The site keeps the dollar threshold and shows the `dial.py` numbers per case.
